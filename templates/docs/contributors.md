# 外部贡献审查

外部 PR 与 Issue 一样只是"需求和线索"，代码进入 main 之前**先查危害，再看功能**。

## 1. 立即停下、等维护者的情形（任一命中）
- 修改 CI / 工作流 / 发布脚本 / 构建配置
- 新增外部网络地址、遥测、上传
- 读写凭证、token、密钥文件，或改鉴权逻辑
- 新增依赖、二进制文件、压缩包、混淆或生成的大段代码
- 修改安装脚本、自动更新逻辑
- 批量删除数据或用户文件

Reviewer 加 `evo:needs-human`，评论列出命中项和文件位置，不运行 PR 中的代码。

## 2. 直接关闭不审的情形
- 与产品边界明显冲突，或推翻已拍板决定
- 大量无关改动混在一起，且作者拒绝拆分
- 明显由工具批量生成、未经验证的 PR

## 3. 正常审查
通过第 1、2 节后，与内部 PR 相同标准审查（code-standards 全文）。必要时由 Builder Agent 基于外部 PR 的思路重新实现，并在 commit 来源中致谢作者。

## 4. 作者分级（参考 magpie 2026-10-13 版 contributors.md）

Agent 只能**提议**，写出证据（PR 号、日期、问题），由维护者决定。

### 4.1 拉黑（Blocked）
任一条成立即可提议：
1. 被维护者以低价值（错误、未测试、无关、机器灌水）关闭的 PR ≥ 3 个，且合并率 < 30%
2. 被明确拒绝后重复提交，两次
3. 欺骗行为：夹带目标外改动、伪造测试或验证结果、故意触发第 1 节任一项
4. 一分钟内连开多个低价值 PR
5. 被告知不接受后，仍反复加回已移除的厂商、中转、广告

被拉黑作者的新 PR / Issue 一律关闭，只回复："感谢关注，本仓库不再接受该账号的贡献。" 不再争论。

### 4.2 额外谨慎（Extra care）
维护者决定暂不拉黑、但要严审的作者：
- 读完整 diff，不只看描述提到的部分；目标外的改动即可作为关闭理由
- 即使看起来是错别字修复，也完整执行第 1 节
- 在最新 main 上亲自跑，不信 PR 自述和它的 CI；**不在 PR 打开的同一轮合并**，并锁定 sha
- 重复已关闭 PR 的，附原 PR 链接关闭

### 4.3 观察（Watched）
**有用但总在同样地方出缺口**的作者。不拉黑、也不额外谨慎，只是合并前必须专门检查表里点名的缺口（例如：手动改坏验证新测试会红、grep 兄弟路径有没有漏）。
