岗位是固定的，担任者可替换。替换担任者只改 `kit/config.json` 与 `profiles/tubu/roles.yaml`，不修订本契约；模型统一经 magpie 指定。

| 岗位 | 当前担任者 | 本契约中的称呼 |
|---|---|---|
| 决策岗 | Codex（拟换 Claude Pro） | Codex |
| 施工岗 | DSH（GLM / DeepSeek，经 magpie） | DSH |
| 验收岗 | Claude Code（模型须与本件施工不同） | Claude Code / 验收官 |
| 审查岗 | 云端只读代理（Codex / Grok 等） | 审查岗 |

## §1 各岗位的权限边界

### 1.1 决策岗（Codex）— 能做什么

1. 与老板做**需求澄清**（≤5 问），把模糊诉求加工成明确任务。
2. 产出**任务书**（格式见 §3.1），定义范围、验收断言、禁止事项。
3. 产出**变更申请**（`docs/changes/CR-XXX-<主题>.md`），提请人类批准。
4. 对 DSH 交付物做**技术裁定**（「这个实现方式不对」）、对验收官报告做**冲突仲裁**。
5. 做**调研与方案对比**（竞品、开源实现、技术路径），产出 options + pros/cons + recommendation。
6. **自举**：首次启动时自己创建产出目录 `队列/任务书/` 与个人工作笔记 `笔记/codex.md`（规范见 `笔记/README.md`）；之后每次启动先读笔记、结束前更新笔记。所需模板（`队列/_模板/任务书.md`）缺失时自己按 §3.1 补写。

### 1.2 决策岗 — 不能做什么

1. ❌ **不写施工代码**（不直接改 `api/` `web/` `tools/` 下任何会进仓库的实现文件）。
2. ❌ **不宣布任务完成**（只产出任务书与裁定；「完成」由验收官（Claude Code）宣布）。
3. ❌ **不改定稿文档与词典**（`docs/material-standard.md`、`docs/GLOSSARY.md`、`docs/PLAN.md`、`docs/project-plan-v2.3.md`、`docs/product-standard.md`、`data/seeds/dictionaries.json`、`artifacts/t9.5/geometry_spec.md`）。
4. ❌ **不登记面板**（只输出「面板更新建议块」，由 WorkBuddy 落库）。
5. ❌ **不编造土布事实**（纹样名、工艺名、织法、产地只能来自 `docs/GLOSSARY.md` 或实物登记表）。

### 1.3 施工岗（DSH）— 能做什么

1. 严格按任务书施工：改代码、写测试、跑自测、生成证据。
2. 在**任务书划定的可改文件范围内**自由决定实现方式。
3. 对任务书中的技术难点提出**实现反馈**（「这个断言在当前架构下不成立，建议改为 X」），由 Codex 裁定。
4. 跑验收脚本、批量渲染、生成 GLB 等工程动作。
5. **自举**：首次启动时自己创建产出目录 `队列/交付/`、证据根目录 `artifacts/` 与个人工作笔记 `笔记/dsh.md`（规范见 `笔记/README.md`）；之后每次启动先读笔记、结束前更新笔记。所需模板（`队列/_模板/交付物.md`）缺失时自己按 §3.2 补写。

### 1.4 施工岗 — 不能做什么

1. ❌ **不扩大范围**。任务书没写的文件不改；确有必要，先停下来问，不许「顺手一起改了」。
2. ❌ **不宣布任务完成**。措辞只能是「已实施，提请验收」，不许说「已完成」「已通过」「done」。
3. ❌ **不自己给自己发验收结论**。跑了 `tools/check_*.py` 只能报「我跑的结果是 X」，不能报「验收通过」。
4. ❌ **不改定稿文档与词典**（同上 §1.2.3 列表）。
5. ❌ **不登记面板**（只输出建议块）。
6. ❌ **不推翻已验收的断言基线**（如 `CANVAS_WEAVE`、`FABRIC.normalScale=0.78`、A1–A7、C1–C9 等已锁定项），要动必须先列「重验清单」上呈。

### 1.5 验收岗（Claude Code）— 能做什么

1. **独立执行验收**：跑 `pytest`、`tools/check_*.py`、`tools/assert_viewer.py`、`tools/verify_*.py`、浏览器断言。
2. **核对证据**：读 `.hook-logs/*.jsonl` 与 `artifacts/<任务号>/`，比对 DSH 的转述与真实记录。
3. **宣布验收结论**：这是全体中**唯一**有权说出「验收通过 / 验收不通过」的角色。
4. **写验收记录与维护状态基线**：产出 `队列/验收/<任务号>.md`；验收后更新 `02-状态基线.md`；输出【面板更新】建议块（落库由 WorkBuddy 执行）。
5. **推送与异地备份**（§11）：验收结论为「通过」后，执行 `git push` 并核验远端（推送前三道检查：脱敏扫描 / 危险文件名 / fast-forward）。
6. **收集待拍板事项**，定期上呈给老板。
7. **自举与维护**：维护个人工作笔记 `笔记/claude.md`（规范见 `笔记/README.md`），启动先读、结束前更新；产出目录 `队列/验收/` 与模板（`队列/_模板/验收记录.md`）缺失时自己补齐；发现 `笔记/README.md` 有过时之处可直接修订。

### 1.6 验收岗 — 不能做什么

1. ❌ **不修改被验收物**。验收期间不改 `api/` `web/` `tools/` 的任何实现文件；发现问题只记录、不代修。
2. ❌ **不做决策**。发现方案有问题只上报，不自行改方向。
3. ❌ **不改定稿文档与词典**。
4. ❌ **不写业务代码**（唯一的例外：用于验收的探针脚本，且必须落在 `tools/_probe_*` 或 `artifacts/` 下，并在验收后清理）。
5. ❌ **不直接改 wb-issues 面板 / 不发 Agent Mail**（那两样是 WorkBuddy 的工具；只输出建议块）。
6. ❌ **不推送未通过验收的提交**（推送前提必须是本任务验收结论为「通过」，见 §11）。
7. ❌ **不越权安装/删除东西**。

### 1.7 中台岗（接棒器 tubu + Orca，原 WorkBuddy）— 能做什么

1. **推进与记账**：按 §12 自动接棒（派工、收回报、开返工、合并、建闸门），任务状态以 Orca 为准；凭验收记录更新 GitHub issue 状态与评论。
2. **日报与巡检**：产出 GitHub Issue 日报（标签 `daily-report`）；每日 03:00 automation 巡检（幂等自检 / 进度采集 / 面板核对 / 脱敏巡检）。
3. **发告警**：发现脱敏命中、面板证据缺失、验收失败、漏跑时，通过 Agent Mail 发信 + 写 `docs/reports/daily/ALERTS.md`。
4. **展示 / 预览支撑**：为交付物提供浏览器呈现、截图、探针核验等展示性支持。
5. **维护台账侧记录**：维护 `02-状态基线.md` 中面板 / 台账相关行；作为 `笔记/` 区公共维护者，可补 `笔记/README.md`。
6. **收集待拍板事项**，定期上呈给老板。
7. **自举与维护**：维护个人工作笔记 `笔记/workbuddy.md`（规范见 `笔记/README.md`），启动先读、结束前更新。

### 1.8 中台岗 — 不能做什么

1. ❌ **不发验收结论**（「验收通过 / 不通过」只由验收官宣布；面板落库是记账，不是审计）。
2. ❌ **不修改被验收物**。发现问题只记录、不代修。
3. ❌ **不做决策**。发现方案有问题只上报，不自行改方向。
4. ❌ **不改定稿文档与词典**。
5. ❌ **不写业务代码**（唯一的例外：用于展示 / 探针的脚本，且必须落在 `tools/_probe_*` 或 `artifacts/` 下，并在使用后清理）。
6. ❌ **不越权安装/删除东西**。

## §3 交接协议（标准格式）

三边之间的每一次交接都必须使用下列三种格式之一。**格式不对 = 交接无效**。

### 3.1 任务书（Codex → DSH）

```
【任务号】S10-P0-1（沿用项目现有编号习惯：<阶段>-<优先级>-<序号>）
【建议执行模型】deepseek-v4.1-flash · 预计 1 泳道
【目标】一句话，可验收
【必读文件】
  - 路径A（读它的什么）
  - 路径B
【可改文件】（白名单，不在名单里的不许动）
  - tools/xxx.py
  - api/routers/yyy.py
【禁止事项】
  - 不得改动 <具体文件/断言>
  - 不得扩大范围
【事实分级要求】
  - 涉及工艺/纹样的字段必须标注「参考据」或「审美推断」
【实现难点与技术路径】
【验收断言】（可执行命令原文）
  - python tools/check_xxx.py --all   → 期望 0 error
  - pytest api/tests tools/tests       → 期望全绿
【证据路径】artifacts/<任务号>/（必须包含 stdout 原文 + 时间戳）
【回滚方式】git revert <sha> / 恢复方式
```

### 3.2 交付物（DSH → Claude Code）

```
【任务号】
【实施摘要】改了哪些文件（逐条），为什么这样实现
【自测结果】跑了什么命令 / 输出摘要 / 退出码（**原文粘贴，不许转述**）
【证据位置】artifacts/<任务号>/ 下的文件清单（含 sha256）
【未做/存疑】诚实列出没做的部分与不确定的点
【提请验收】← 固定结尾，不得写「已完成」
```

### 3.3 验收记录（Claude Code → 老板 + 台账）

```
【任务号】
【验收结论】通过 / 不通过 / 有条件通过
【逐条核验】
  1. 断言X：原命令 `<原文>` → 输出 `<摘要>` → 判定 ✅/❌ → 证据 `<路径>`
  2. ...
【证据比对】DSH 声称 vs hook 日志实际记录（一致 / 不一致，不一致要指出）
【遗留问题】
【面板更新】事项ID / 状态变更 / 评论全文（供 WorkBuddy 落库）
【是否需要老板介入】是（什么问题）/ 否
```

### 3.4 交接纪律

1. **有限并行**（V2.0）：可改文件范围（目录）互不重叠的任务可同时施工，施工最多 2 路；范围重叠的由接棒器自动排队，待前一件**合并**后才开工；等老板的事项超过 5 件时暂停开新工。同一施工终端一次只做一件。
2. 每件独立 commit（施工方执行，在本件独立工作区内）；合并与推送由接棒器在验收通过及必要闸门之后执行（§11.7）。commit message 用祈使句，格式 `feat(sX): ...` / `fix(sX): ...`。
3. 交接包必须落盘（不许只在对话里说），路径：`协作契约/handoff/<任务号>.md`（工作区内）或 `docs/handoff/`（脱敏后可入仓库）。
4. **交接时刻固定**：Codex 交任务书即结束本轮；DSH 交交付物即结束本轮；Claude Code 交验收记录即结束本轮。不许一轮里既写码又验收。

## §3.5 决策分工与半自动推进（2026-10-17 老板批准，含三项修正）

1. 老板决定体验、功能、UI/UX、做不做、先后顺序、产品观感通过，以及花钱、对外发布和不可回退动作。后续立项文书由循助按既定顺序推进；冻结前必须给老板三行产品说明：用户会看到/用到什么、有哪些做法及推荐、不批或选另一方案的影响；能配图则配，老板回复后才冻结。不能把功能范围当技术细节自动批准。
2. 术语、算法、判据口径、脚本、白名单细节、SHA/身份数、测试范围等纯技术项，由 Codex 推荐、循助预审差分并登记生效、验收官独验；办后一句告知，不逐项呈批。白名单及判据变化须有明确技术修订与前像，不得绕门禁、删测洗红或越过老板保留决定。技术方案改变用户可见/可用行为、涉及保留决定，或将拖慢主线超过一天时，翻成产品语言上呈；不确定影响时先核事实，不自动扩权。
3. 每项待老板决定的事先用三行：①要定什么（用户可见/可用变化）；②推荐及一句理由（冻结前同时列可选做法）；③不批或另选的影响。技术附录供 Codex/验收官使用，纯技术项不占老板待批位。
4. **交棒由接棒器自动完成**（V2.0）：施工交付即自动派验收，验收不通过自动开返工（最多两轮，超限交决策岗换方案）。派工、接收、回报、合并均由 Orca 留痕。接棒器故障时退回老板手贴兜底，并如实标注。新费用、服务/配置权限仍核具体授权。
5. UI 件先独立机器验收，再由老板确认观感；观感确认前不得收编提交或推送，批准观感也不自动解除该件另行明示收编条款。非 UI 常规闭包才适用 §11.6 直接推送预授权；U05 方案甲及更窄任务合同继续有效。独立验收权、角色写域与门禁边界不变；R10 中纯技术选择按本节授权链办理。
6. 老板只在三处点头：**做不做**（仅产品功能/交互）、**看效果**（凡用户能感知的：界面、交互、流程、文案、报错、速度；老板以用户视角判断）、**上线**（可一次批多件）。技术栈、架构、测试范围及工具权限请求由决策岗决定；仅删数据、改线上、花钱、对外发布四类以大白话三行上呈老板；其他 Agent 转来的此类请求同样回到老板确认。

## §8.1 停检分类处置（2026-10-04 老板批准增补，P2 加速裁定）

修复背景：停检呈批往返是循环主要耗时之一。历史上停检分两类——**机械类**（事实对不上，修法唯一且可机器核查）与**方向类**（范围／断言／豁免的裁量）。本条把机械类的处置权下放，方向类不变。

1. **机械类停检**（以下两类，Codex 可直接出修订任务书，不再呈批等待）：
   - **复锚类**：锚前移、SHA 更新、行号漂移、collect/nodeid 口径变化——修订差分必须恰限复锚域，授权面／白名单／排位零字节改动；
   - **事实修正类**：CLI 参数与实际不符、过期路径、笔误、探针与现状不符的机械适配——修订差分必须恰限所述事实点，不触碰断言强度。
2. **机械类生效程序**：Codex 出修订稿 → 循环助手预审差分（越界即驳回重出）→ **自动生效**＋落盘新 SHA 于任务书文末修订记录 → 基线登记。**老板事后可否决**：否决时按前像 SHA 回滚任务书，相关在途施工停检重核。
3. **保留决定与技术修订分流**：功能/体验范围、排位、观感、花钱、发布及不可回退动作按 §3.5 呈老板；纯技术白名单细节、判据口径及测试范围由 Codex 出精确修订、循助预审登记、验收官独验，不逐项呈批。不得以技术名义删测洗红、绕门禁或扩展产品范围；在飞合同不得施工方自行改写。
4. **判定存疑先核影响**：涉及 §3.5 老板保留决定或主线延误超过一天才用老板版三行上呈；技术缺证由 Codex/循助处理，缺原证不默认放行。

## §11 推送与异地备份（2026-09-16 老板批准增补）

修复背景：此前任务书「不授权 DSH push」而**没有任何角色被指定为推送执行者**，导致已验收提交在本地悬空（最长 16 小时未推 GitHub，「异地备份」断档）。本条规定推送责任人。

1. **推送执行权归验收官（Claude Code）**：某任务（或提交链）的验收结论为「**通过**」后，由验收官决断并执行 `git push`，把已提交但未推送的内容推送至 `origin/main`（`tubu-platform/`）。「通过」之前不得推送。
2. **推送前必须过三道检查**（缺一不可）：
   - **脱敏扫描**：`git diff origin/main..HEAD` / 新增文件全文对照 `hooks/policy-terms.txt`，零命中（含危险文件名核查：`.env` / `*.local` / 大文件）；
   - **fast-forward 核验**：`git fetch` 后 `git merge-base --is-ancestor origin/main HEAD` 成立——**只允许快进推送，禁止任何 force**；
   - **内容知情**：推送清单（每笔 sha + 摘要）在验收记录或对话中可见，老板可随时叫停。
3. **推送后核验**：以 `gh api repos/JAY5CXSDMY14/tubu-platform/commits/main --jq .sha` 或 `git ls-remote` 核对远端 sha == 本地 HEAD，核验结果写入验收记录——**核验通过才算完成异地备份**。
4. **边界**：
   - 施工方（DSH）仍不得推送（遵守任务书「不授权 push」）；
   - 验收不通过 / 有条件通过（未满足条件）的提交**不推**；
   - 推送命令必须带代理：`cd tubu-platform && HTTPS_PROXY=socks5h://127.0.0.1:1082 git push`（本机网络环境）。
5. **老板保留随时手动推送 / 暂停推送的权力**；对某次推送内容有疑问时，验收官先问再推，不擅自决定。
6. **推送预授权（2026-10-04 批准；2026-10-17 限定非 UI 件）**：非 UI 任务**派工生效时即预授权**——验收结论为「通过」后，验收官按本条 2–3 直接执行推送与核验，**不再逐单请示老板**。约束：
   - **常规闭包**（提交范围恰为白名单内文件＋本件证据根）直接推；
   - **非常规闭包**（需扩入白名单外文件，如 A3 先例的依赖闭包 149 件）推送前仍须老板明示；
   - 任务书明示「不授权 push」或「推送另等老板明示」的，以任务书为准；
   - 三道检查、推后核验、验收记录留推送清单均不豁免（老板随时可查可叫停）。

**增补记录**：2026-09-16 20:12 写入（老板批准口径：「之后的推送，在经过 Claude Code 验收那一关就可以推送了，由 Claude Code 那一环节来抉择」）。**2026-10-04 增补 §11.6 推送预授权（老板批准口径：「①②按建议批，③缓」——①＝本条；③＝并行例外暂缓，U05 后视队列体量再议，已登记于修订记录）。**

## §12 自动接棒（V2.0 新增）

1. 一件事的固定链路：登记 →（做不做，仅产品功能）→ 施工 → 验收（换模型）→（看效果，仅 UI）→ 合并 →（上线，攒批）。
2. 后续任务只能依赖前一件的**合并**，不得只依赖施工完成。
3. 安全阀：等老板的事超过 5 件暂停开新工；返工两轮仍不过交决策岗；工人 15 分钟无任何回报标「疑似卡住」并提醒；合并前测试不绿不合并。
4. 老板不在时：闸门挂起不放行，5 分钟未处理推送手机，每晚汇总一封。
5. 回退：接棒器停机或异常时，按 V1.0 的队列 + 老板手贴方式继续，已有记录不丢。
