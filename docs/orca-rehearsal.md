## A 结论
```callout ok 在 Hark 沙箱里跑通了
Orca 1.4.232 以无界面服务端跑在 Linux ARM 上。用一个副本仓库演了三件事：两件不冲突的并行开工，冲突的一件被自动挡住，你的「看效果」闸门挡住后续，点通过后才放行。
```

## B 实测结果
| 环节 | 怎么测的 | 结果 |
|---|---|---|
| 无界面运行 | orca-ide serve，Linux ARM | ok 正常，终端守护自检通过 |
| 每件独立工作区 | 每件一个 worktree 和分支 | ok 自动建好 |
| 不冲突并行 | A 改 web，C 改 api，同时派工 | ok 两件同时在做 |
| 冲突排队 | B 也改 web，依赖 A | ok 派 B 被拒，提示依赖没完成 |
| 完工回报 | 施工方发 worker_done 和心跳 | ok 统筹方收到，任务变成已完成 |
| 你的闸门 | 给 B 加「A 效果通过了吗」 | ok B 被挡住，点通过后才放行 |

## C 发现的坑
| 坑 | 说明 | 对策 |
|---|---|---|
| 依赖放行太早 | A 一交付，B 就放行了，还没验收和合并 | warn 每件拆成施工、验收、合并三步，B 依赖「A 合并」 |
| 回报靠 Agent 自觉 | worker_done 要施工 Agent 按说明自己发 | warn 我们的 Hook 守护继续兜底，查无交付就报停滞 |
| 没跑真 Agent | 沙箱里没有你的 Codex、Claude 账号 | 最后一步在 Mac mini 上接 |

## D 我们的设计怎么落到 Orca
| 我们的环节 | Orca 里用什么 |
|---|---|
| 任务书 | task-create，写清范围、依赖、是否 UI、验收命令 |
| 做不做 | 施工任务上的闸门，你点了才派工 |
| 施工 | worker-start，指定施工模型 |
| 验收 | 独立任务，依赖施工，换另一个模型 |
| 看效果 | 合并任务上的闸门，只有 UI 件才加 |
| 合并 | 合并任务，重跑测试后合，不强推 |
| 上线 | 部署任务上的闸门，可以攒一批一起点 |
| 停滞 | 心跳加 worker-show，Hook 守护兜底 |
| 统一入口 | GitHub issue 直接开工作区 |

## E 每件事的流水
```flow LR
[issue] -> [做不做 闸门] -> [施工] -> [验收 换模型] -> [看效果 闸门 仅UI] -> [合并] -> [上线 闸门 可批量]
```

## F 还要在 Mac mini 验的三件
1. DSH 当自定义命令行接入，Hook 照常记日志。
2. 手机 App 在等权限、等闸门时能提醒你。
3. 真 Codex 统筹时，能守住「施工和验收换模型」「范围重叠就排队」。
