# 《Context 与 Loop》对 evo 的启发（摘编 + 落地建议）

> 来源：张立行《吃一堑，长一智：Agent 时代的两个关键词 Context 与 Loop》，X 长文，2026-10-04（x.com/i/article/2106757373834780723，博客 zj1123581321.com/posts/261004-context-and-loop/）；WY（@wangyuanzju）2026-10-22 转发评论「software-factory」。2026-10-23 读原文整理。
> 作者的体系 = 主脑（拆任务/判断/验收）+ 执行器（Pi + 便宜 Flash 模型）+ 门禁，和 evo 的 决策岗 + DSH 施工 + 验收 + 老板闸门 几乎同构。下面只记对我们有用的，按「建议马上做 / Claude 接入后做 / 先不做」分组。所有条目都是提议，等老板点头。第 1–6、14 条老板已批，第二十二轮做完（kit/README.md 第二十二轮）。

## 一、建议马上做（便宜、风险低）

1. **行为轨迹永久保存**。✅ 第二十二轮已做（`runs/<件号>/`，`evo -p X runs`）。Claude Code 默认 30 天删本地会话（`cleanupPeriodDays`）。evo 每件活的施工/验收/决策日志、Multica run 记录按件归档进 `~/.evoloop/projects/<CODE>/runs/`，不自动删。后面的复盘、规则体检、回测都靠它。
2. **判据先喂一个「应该变红」的输入**。✅ 第二十二轮已做（`evo canary`，selfcheck 也跑；跳过算通过的几处已修）。作者踩的坑：草稿 PR 跳过审查被汇总当成「通过」；考审查模型的合成考卷因凭据没配一次没判过，跑了 111 次全绿。evo 对应：验收岗、闸门判定、`in_scope()`、报告解析，每个都配一条已知不合格的样例（金丝雀件），定期跑，确认会判不过。原则：**永远不会变红的检查等于没写**。「跳过」绝不能算「通过」。
3. **规则注入硬上限**。✅ 第二十二轮已做（test_round22_sizes.py：施工 15800 / 验收 13500 / 决策 8000 字节）。作者：主脑侧 ≤24KB、执行器侧 ≤12KB，超了提交直接拒。evo：给 `kit/roles/*` + 预设块 + 任务书拼出来的总字数加测试上限（决策 / 施工 / 验收各一档），想加一条规则先删一条。
4. **执行器只拿执行器要的东西 + 角色声明**。✅ 第二十二轮已做（施工任务书首行固定角色声明；施工拿到决策岗规则时自动换回施工岗规则）。作者踩坑：任务卡没写「你是干活的，不要再派」，执行器读到主脑的派发手册，把活又派出去空转 90 分钟。evo：施工任务书开头固定一句角色声明；施工岗拿不到决策岗的规则段。（检查现状，缺的补上。）
5. **教训单的关单标准**：✅ 第二十二轮已做（错题本 Mechanism 字段 + 「已关单」一节，lessons.py lint 查）。不是「修了」，而是「机制上不可能再发生」。错题本里的每条教训，优先沉淀成 测试 / 脚本 / 闸门 / hook，其次才是写进规则文字。强弱顺序：代码结构 > 静态检查 > 规则/技能 > 靠人审。
6. ✅ 第二十二轮已做（推送和远端租约都用 git ls-remote 确认）。**确认推送是否成功一律问远端**（`git ls-remote` / GitHub API），不看本地输出。evo 合并/推送路径检查一遍。

## 二、Claude Pro 接入后做

7. **Advisor 模式 = 我们决策岗的正确用法**。要点：
   - 顾问用最强模型，**而且上下文是干净的**：不带施工和之前几轮的对话，只给任务书、代码、diff、机械事实。作者盲测 9 次，干净上下文的顾问 9 次都否掉了主脑「再修一轮就收尾」的计划。
   - 顾问在只读沙箱里，能看不能改。
   - 请教卡三栏：机械事实 / 我的判断 / **我希望听到的答案**（专门留给顾问反驳）。
   - **什么时候请教靠机械信号，不靠模型自觉**：返工轮次用完、验收连续两轮出新问题、卡太久、定方向前。evo 已有「2 次决策返工上限」，正好接这个触发点。
   - 对应 Claude Pro 额度：只在这些节点调用，不常驻。
8. **一份底稿，按「工具 × 角色」拼接，不按模型拆**。共用底座（工程习惯、不重复造轮子）+ 决策岗专属 + 工具专属（如 Codex 侧带完整「反过度设计」）。我们已有 红线/接口/现状 三层，可以再加「工具段」。
9. **新工具先用自己日志回测再装**（作者装了 RTK 又卸了：宣称省 90%，实测省 44%，但省的都是不该压缩的搜索/读文件）。和规则体检同一套机制。

## 三、需要注意的反向提醒

10. **「方向照着走，节奏晚半年」**：Anthropic 删 80% 提示词的前提是顶级模型 + 几乎无限 token。我们施工用的是便宜模型（DSH free-ds、glm-flash），给便宜模型打的补丁暂时别删。第二十一轮瘦身只动了重复和互相矛盾的内容，没删施工岗的执行细节，方向是对的；以后再瘦身施工岗要先做规则体检，有数据再删。
11. 作者结论：执行器外壳不是胜负变量，**差距主要来自喂给模型的上下文**（他修掉 3 类注入问题后，Pi 首轮输入从 1.75 万 token 降到 8500，质量持平略优，成本降约 40%）。值得用同样方法查一次 DSH 施工时实际吃进去多少上下文。
12. Mac 上很多权限要人点「允许」，循环会断；纯后端循环 Linux 更顺。我们 iOS/Swift 项目离不开 Mac，暂不动，但新增机器优先考虑 Linux 跑纯后端的施工。

## 四、WY「软件工厂」说法

一个专门的项目持续积累 规范 + skill + hook，各项目共享；全局规则 + 项目分层规则 + 项目专属 skill/脚本 + 重要模块 PRD/架构要求，一起构成流水线。**这就是 evo 自己（EV 项目）的定位**：各项目遇到调度层面的问题都回报到 evo 仓库 issue，EV 每天处理。作者的 agent-config 两个月 1800 个 issue，其中 1100 张是教训单，每周新开数从峰值 305 回落到 159，说明循环在收敛。

## 五、补充：Claude Code「动态工作流」与「先考考官」（2026-10-23 读）

来源：xsmryze X 帖 2026-10-22（夸张营销腔，帖里的「JEV」是推广，不采用）；官方文档 code.claude.com/docs/en/workflows（2026-10-23 打开）；NO1ennn《How to Turn Opus 5.5 Into a Reverse Engineer》2026-10-14，引 REA 博客 N0zoM1z0 2026-10-10。

13. **动态工作流 = 强模型写编排脚本，便宜子代理并行跑，强模型只看验证过的结果**。evo 本身就是这个结构（决策岗写任务书 → DSH 施工 → 验收 → 决策只看报告），不用换。可借的点：
    - Pro 上要在 `/config` 打开 Dynamic workflows，默认规模 small（<5 个代理），会明显多吃额度。
    - `ultracode` 关键字在 `claude -p` 里不会触发；`-p` 下工作流要靠权限规则 `Workflow` 放行。所以 **evo 的无人值守决策调用不开工作流**，只在老板手动跑冷启动审查时可以用（「每条发现交给独立代理对抗复核后再报」）。
    - 官方示例「修到检查通过，或连续两轮没进展就停」与我们 2 次返工上限一致。
14. **先考考官（planted failures）**：✅ 第二十二轮已做（并入第 2 条：金丝雀测试用三变体改坏判据；验收岗可选「埋雷: 是」）。REA 重建 TH08 时，一个函数已通过逐字节比对，实际常量错了（0.0 应为 128.0），因为比对工具不查常量本身；补查后在已「通过」的 1548 处里又挖出 12 个错。做法：信任一次全绿之前，先给判据喂三个必须失败的变体（改一个常量 / 换一个分支 / 边界挪一位），有一个通过就先修判据。和第 2 条合并实施：验收岗每件活可选「埋雷」三变体。
15. **净室式交接**：读的人只写 SPEC（行为、输入输出、边界、未知），干活的人只拿 SPEC。印证 evo「决策写任务书、施工只拿任务书」，任务书里要把「未知」写出来，不要让施工去猜。
