## A 结论
```callout ok 两件都能做，而且不冲突
Ponytail 本质是一段 MIT 提示词。施工岗用主规则，验收和审查岗用 review 清单，夜审可加 audit。默认模型放在 magpie 里设：magpie 建「施工组」「验收组」，evo 只认组名，换模型在 magpie 里点一下，所有项目一起生效；面板里再给单个项目一个覆盖下拉框。
```

## B Ponytail 是什么
| 项 | 内容 |
|---|---|
| 仓库 | DietrichGebert/ponytail，MIT，最近更新 2026-10-18 |
| 本体 | 一段提示词 skills/ponytail/SKILL.md，加精简版 AGENTS.md；其余是装进 20 种 agent 的适配 |
| 主规则 | 先读懂改动波及哪里。再按台阶选最小完整改法：不需要就不做 → 仓库已有就复用 → 标准库或平台自带 → 已装依赖 → 一行 → 最少代码 |
| 底线 | 校验、防数据丢失、安全、无障碍永远不砍；有分支、循环、解析、钱或安全的逻辑必须带一个小测试 |
| 收尾 | 每次回复写明跳过了什么、没查什么、有什么风险 |
| review | 读 diff 加上下游调用方；按 正确 → 安全 → 负载 → 测试 → 速度 → 精简 排；每条发现要有具体触发情形，分 必须修 / 应该修 / 锦上添花 |
| audit | 整仓体检，按优先级排出先修哪个 |
| 效果 | 作者自测：代码少 53%，token 少 45%，高风险逻辑带测试 98%（不用时 68%）。是作者自己的基准，当参考 |

## C 放进 evo 的哪里
| 岗位 | 用法 | 和现有规则的关系 |
|---|---|---|
| 施工 | 主规则 full 档并进 roles/builder.md；不用 ultra（ultra 会质疑需求，需求已经过你和决策岗） | 和「先写会失败的测试」「列出没跑的」一致；它的收尾正好填进 JSON 交卷的 unfinished 和 risks |
| 验收 | review 清单并进 roles/verifier.md：必须修 = 打回，应该修 = 记 issue 不挡合并 | 现有验收看测试和契约，补上「读调用方」和「每条要有触发情形」，误报会少 |
| 审查（云端） | 审查岗跑 review，结果按三档开 issue | 审查岗只读 GitHub、只开 issue，不变 |
| 夜审 | 每周一次 audit，前三条开成 issue 进决策岗 | 不进夜审每天的流程，避免 issue 太多 |

```callout warn 三条注意
1. 只取官方仓库，固定到一个提交。把两段提示词拷进 kit，不装插件和 hook。作者升级时我们看过再跟。
2. 它会写 shortcut: 注释记欠账，夜审把这些收集成 debt 清单。
3. 它的「最少代码」不能压过任务书的验收标准；冲突时以任务书为准，这句写进施工提示。
```

## D 默认模型在哪设
evo 现在：项目配置里每个岗位有一张模型表。开工时把模型名填进命令（{model}），返工换下一个。验收自动挑一个和施工不同的模型。模型名就是 magpie 的模型 id，本来就走 magpie。

| 方案 | 怎么设 | 好处 | 问题 |
|---|---|---|---|
| 1 evo 配置里写死 | 全局或项目配置写 magpie 模型 id | 已经能用 | 换模型要改文件；magpie 那边下线一个模型，evo 不知道 |
| 2 magpie 建组（推荐） | magpie 里建 group/evo-build、group/evo-verify，evo 只写组名 | 换模型在 magpie 界面点；一个模型额度满了 magpie 自动换下一个；所有项目一起生效 | 两个组的成员不能重叠，否则「施工和验收不同模型」可能被打破 |
| 3 面板下拉覆盖 | 面板项目页加「施工模型」「验收模型」下拉，选项读 magpie 的 /v1/models | 单个项目能单独指定，比如 ST 用更强的模型 | 要加一点面板代码 |

**推荐 2 加 3**：默认值放 magpie 的组，面板只做单项目覆盖，覆盖写进项目配置，清空就回到组。

## E 会不会和 magpie 冲突
```callout ok 不冲突，各管一层
magpie 管「有哪些模型、用哪个账号、额度满了换谁」；evo 管「哪个岗位用哪个组」。magpie 给每个 agent 设的默认模型只在 evo 没指定时生效；evo 开工时显式传模型，只影响那一次，不改 magpie 的设置。要注意的只有一条：施工和验收的组成员别重叠，evo 装机时检查一次，重叠就提示。
```
