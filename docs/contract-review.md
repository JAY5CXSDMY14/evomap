## A 结论
```callout warn 契约本身有三处和新设计正面冲突，要先走修订
一是「老板是唯一推进信号源」，二是「一轮只做一件、不开并行」，三是「面板唯一真源是 WorkBuddy」。这三条不改，自动接棒、并行收菜、issue 统一排队都落不了地。按契约 §10，AI 只能提建议，修订要你批。
```

## B 和新设计冲突的条款
| 条款 | 现在写的 | 冲突在哪 | 建议改成 |
|---|---|---|---|
| 03 §6、§7 | 老板是唯一推进信号源，刻意不自动 | no 自动接棒 | 中台按岗位自动接棒，你只管三处点头 |
| 01 §3.4 第 1 条 | 一轮只做一件，不许并行 | no 并行收菜 | 改动范围不重叠才并行，施工最多 2 路 |
| 01 §3.5 第 7 条 | 不开第二 DSH，串行 | no 并行收菜 | 同上，按工作区隔离 |
| 01 §7 | 面板唯一真源是 wb-issues，只有 WorkBuddy 能改 | no 统一排队 | 事实源改为 GitHub issue，面板只显示 |
| 01 §3.5 第 4 条 | 没有投递通道就交老板手贴 | warn 把复制写成了常态 | 由中台投递，手贴只作故障兜底 |
| 01 §11 | 验收官执行推送 | warn 和自动合并重叠 | 合并由中台在闸门通过后执行 |

03 §7 当初写过：跑满 20 件以上再讨论自动触发。现在任务书 127 份、验收 89 份，这个条件已经满足。

## C 契约自己的问题
| 问题 | 证据 | 影响 | 建议 |
|---|---|---|---|
| 写死工具名 | 标题仍是「三智能体」，全文点名 Codex、DSH、WorkBuddy | 换人就要改契约 | 改写成岗位，担任者放 roles.yaml |
| 权威文件太大 | 当前顺序 411KB，状态基线 348KB | Agent 读一次就耗掉大量上下文 | 当前状态只留一页，历史归档 |

## D 新设计必须遵守的旧条款
| 条款 | 对新设计的要求 |
|---|---|
| §6 脱敏 | ok 网页反馈和 Agent 建 issue 前，必须先过 policy-terms 词表，命中就不建 |
| R7 禁 force push | ok 自动合并不能「改写历史再强推」，用 GitHub 的合并或压缩合并 |
| R9 验收独立 | ok 同一件的施工模型和验收模型必须不同 |
| §4 验收即命令 | ok 自动合并前必须重跑对应命令，全绿才合 |
| §8 例外上报 | ok 不确定的土布事实、版权素材仍然交你 |

## E 建议的修订顺序
```flow LR
[1 契约改写成岗位] -> [2 事实源改 GitHub issue] -> [3 去掉人工推进，改自动接棒] -> [4 开放有限并行] -> [5 合并权交中台]
```
每一步单独一份修订提案，你批一条落一条。先在副本仓库试跑，再改主线契约。
