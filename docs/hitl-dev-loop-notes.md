## A 结论
```callout ok 值得借 6 处，方向不用改
mu-zi-lee/hitl-dev-loop 和 evo 是同一类东西：主 Agent 拆活，编码 Agent 在独立 worktree 里干，调度脚本判定完成、验证、合并，人只看效果和拍板。它是 Claude Code 插件加 bash 脚本，单机、单项目。evo 已经多出了多项目、GitHub issue 队列、手机通知、夜审错题本和外部 Agent 接口。它强在「施工这一段」抠得更细，有 6 处值得直接搬进 evo。
```

## B 值得搬进 evo 的
| 优先 | 它怎么做 | evo 现在 | 建议 |
|---|---|---|---|
| 1 | 施工交卷是 JSON，按 schema 强制：状态、改动文件和原因、实际跑过的测试、未完成项、风险、人工检查项 | 交卷是自由文字，靠解析 | 加 report.schema.json，施工岗必须按它交卷；状态面板和看效果闸门直接用其中的 manual_checks |
| 2 | 改到 scope 以外的文件，调度器直接打回 | scope 只用来排队防冲突；合并前只拦危险文件 | 合并前加一条：改动文件必须落在本件 scope 内，否则返工 |
| 3 | 每轮之后检查并复原 .git/config 里的 core.worktree、core.bare；已被改坏就拒绝启动 | 没有 | 直接加。多 worktree 并行时 Agent 改坏它，主目录所有 git 命令都会指错地方 |
| 4 | 派工前用 git merge-tree 预测和集成分支会不会冲突 | 只按目录前缀判断重叠 | 目录重叠之外再加一次真实冲突预测，减少「对齐主线冲突」返工 |
| 5 | 每件有时长和 token 硬上限，超了停在 budget-exceeded | 只记用量，异常才通知 | 加可选硬上限，默认关；超限停下交决策岗 |
| 6 | 任务默认不开网络，需要时单独开 | 没区分 | 外部 issue 正文本来就当不可信，施工默认断网更稳；需要联网的件由决策岗标出 |

## C 可以顺手借的
- CI 同时跑 ubuntu 和 macOS：evo 最终跑在 Mac mini，launchd、Keychain、路径差异在 macOS runner 上更早暴露。
- 反馈送达三段式：待送 → 送出中 → 已确认，那一轮失败就重发。evo 打回原话已经写进返工任务说明，丢失风险小，只在 Telegram 原话入口补一次确认即可。
- 角色规则加一句：集成出问题先让代码把状态码、内容类型、最终网址、脱敏片段打出来，再猜原因。
- 施工岗只跑相关测试，全量由调度器在提交后跑一次。evo 的全量测试锁已经是这个思路，写进施工岗规则即可。

## D Codex 踩坑清单（上 Mac mini 时核对）
| 坑 | 对 evo 的意义 |
|---|---|
| codex exec 常常说一句进度就结束 | evo 用交互终端不用 exec，影响小；若以后改 exec 要自动续跑 |
| stdin 不关就一直等输入 | 同上 |
| 启动失败也会先发 thread.started | 判断成败要同时看退出码和失败事件 |
| Codex 沙箱写不了 worktree 的 git 索引 | 真机验证施工岗能否自己提交；不行就改成 evo 代提交 |
| goal 功能会给自己设极小预算卡住 | 不依赖它 |

## E 不照搬的
| 它的做法 | 为什么 evo 不跟 |
|---|---|
| 每次推送、合并主线都要你点头 | 你已决定只在做不做、看效果、上线三处点头，推送是流水线一步 |
| 主 Agent（Claude）逐个看 diff 再批准 | evo 用换模型验收加 patch-id 校验，审查岗放云端 |
| 状态全在本地 .agent-loop/，任务队列是 TASKS.md | evo 以 GitHub issue 为唯一入口，状态在 ~/.evoloop |
| 提示音响到你点停 | evo 用 Telegram、邮件、晨报，夜里不打扰 |
