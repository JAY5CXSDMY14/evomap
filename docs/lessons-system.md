# 错题本机制（LESSONS.md）

错题本是 evoloop 的"记忆"。路由表谁都会写，真正让循环自我进化的是这一套：**记录 → 计次 → 升级 → 被执行**。

## 1. 条目格式（严格）

```markdown
### L-0007 先在报告人用的界面上原样复现，再说修好了
- **Why**: 只修了截图里那一个场景，其它入口仍坏，Issue 来回返工。
- **Evidence**: #834 返工 4 次（v0.1.920 → .925 → .931 → .938），每次只修截图里那个 agent：`a1b2c3d`、`d4e5f6a`。
- **Do**: 复现步骤写进测试；列出所有入口（CLI / GUI / API），逐个验证。
- **Done right**: `9f8e7d6` 先用报告人的原始配置文件复现，再修，一次通过。
- **Seen**: 2× (2026-10-05, 2026-10-07)
- **Category**: 读懂报告
```

字段规则：
| 字段 | 必填 | 规则 |
|---|---|---|
| 编号 `L-xxxx` | 是 | 递增，永不复用，升级或废弃后也保留 |
| 标题 | 是 | 一句祈使句，可执行、可检查；不写"注意 xx"这种空话 |
| Why | 是 | 不遵守会发生什么 |
| Evidence | 是 | 至少一个真实存在的 sha 或 Issue 号；`lessons.py verify` 校验 |
| Do | 否 | 具体命令或检查方法 |
| Done right | 否 | 正面案例，同样带 sha |
| Seen | 是 | `N× (日期, 日期…)`；N = 不同日期数，同一天出现多次只算一次 |
| Category | 是 | 见下方分类 |
| Mechanism | 否（关单时必填） | `<kind> — <指向>`，kind ∈ code / test / script / gate / hook / static / rule / review；code～static 级要写指向（路径、`sha` 或 #issue）。第二十二轮新增 |

**关单标准（第二十二轮）**：一条教训不是「修了」就关，而是**机制上不可能再发生**才关。强弱顺序：代码结构（code / test / script / gate / hook）> 静态检查（static）> 规则/技能（rule）> 靠人审（review）。只有 code～static 级、写了指向的条目才能挪进 LESSONS.md 的「已关单」一节，`lessons.py lint` 会查；只写进规则文字或靠人看的，留在活跃教训里继续计次。`lessons.py stats` 会列出还没有机制的条目数（not yet mechanical）。

## 2. 分类（可按项目调整）

1. 读懂报告 — 复现、原始数据、修原因而非文案
2. 修一类不修一例 — 兄弟路径、同形态守卫、所有调用方
3. 用户数据与设置 — 默认值不覆盖用户值、读失败=未知、删除前查全
4. 验证 — Red/Break check、隔离环境、真实使用、Not run
5. 并发与测试 — 测试启动的东西随测试结束、时序测试留余量、flaky 找根因
6. 红测试与发布 — main 红即 bug、CI 全绿才发、攒批
7. 合并与关闭 — 审过的 sha、先写记录再合、报告人确认再关
8. 协作 — 认领、worktree、一个 commit 一个目标

## 3. 生命周期

```
新发现 ──▶ Seen 1× ──▶ Seen 2× ──▶ Seen 3×（3 个不同日期）──▶ 升级为硬标准
                                                         │
                                                         ▼
                                   docs/code-standards.md「来自复盘的硬标准」
                                   LESSONS.md「已升级」区保留指针，继续记录违反/做对
```

- **升级**：Seen ≥ 3 → 写入 code-standards，编号沿用（`S-L0007`），Reviewer 从此逐条核对。
- **降级/废弃**：连续 30 天无新 Seen 且相关代码已删除 → 移到「归档」区，写明原因。不直接删除。
- **合并**：两条实质相同的教训 → 保留编号小的，另一条标 `merged into L-xxxx`，Seen 日期合并去重。
- **反向证据**：如果一条规则导致了新的返工（规则本身错了），Retro Agent 新增一条修正教训，并把原条目标 `disputed`，交维护者决定。

## 4. 为什么是"3 个不同日期"

- 同一天多次出现，可能只是同一个会话的同一个误解，不代表系统性问题。
- 跨 3 天说明不同会话、不同任务都会掉进去：这是**规则缺失**，不是个体失误。
- 太低（1×）会让 code-standards 膨胀成没人读的清单；太高会让同样的错犯一周。
- magpie 截至 10-12 约有 8 条按此规则升级，code-standards 依然可读。

## 5. 文件结构

```markdown
# LESSONS

> 本文件由每晚复盘 Agent 维护。所有 Agent 改代码前必须读完。
> 机制见 evoloop/docs/lessons-system.md。

## 复盘日志
### 2026-10-12（窗口 a1b2c3d..e4f5a6b，58 commits，v1.4.2 → v1.4.5，所有 tag 均在绿色 CI 上）
- 新增 L-0012、L-0013；L-0007 Seen 3× → 升级；Done right 2 条。

## 活跃教训
### 1. 读懂报告
### L-0007 …
...

## 已升级为硬标准
- L-0003 → S-L0003（2026-10-09）…

## 归档
```

复盘日志只保留最近 14 天，更早的移到 `docs/lessons-archive/YYYY-MM.md`，避免 LESSONS.md 过长挤占 agent 上下文。目标长度：**活跃教训 ≤ 40 条，全文 ≤ 600 行**。
