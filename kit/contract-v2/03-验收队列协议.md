# 03 · 验收队列协议（验收官嵌入循环的方式）· V2.0 草案

- 起草：2026-09-15
- 状态：已批准（2026-09-15）；**2026-09-16 修订**：验收官载体由 WorkBuddy 转移至 Claude Code，WorkBuddy 转为面板 / 自动化官
- 解决什么问题：老板提出现有循环是「Codex 商定 → 复制 prompt 去 DSH 执行 → 回 Codex 验收」，**独立验收官怎么插进去**？
- 一句话答案：**把「交接物」从聊天记录变成队列文件**。验收官不介入对话流，只在队列的固定节点上作业。

---

## §1 老板的现有循环（先描述清楚，再谈改造）

老板当前的实操路径（从他的原话还原）：

```
① 在 Codex 里商定任务（对话）
② 把 Codex 产出的 prompt 复制出来
③ 粘贴到 DSH 里执行
④ DSH 干完活，把结果拿回 Codex
⑤ Codex 检查结果、做下一步决策
   → 回到 ①，循环
```

**这个循环的问题**（也是老板要「独立验收官」进来的原因）：

| # | 问题 | 后果 |
|---|---|---|
| P1 | 「验」和「谋」由同一个角色做 | Codex 既设计方案又判断方案做得对不对——自己判自己的卷 |
| P2 | 步骤 ② ③ ④ 全靠人肉搬运 | 老板是唯一的传输通道，内容容易丢、容易走样 |
| P3 | 检查依据是 DSH 的**转述** | DSH 说「跑了，全绿」，没有独立记录可核对 |
| P4 | 验收结论不落盘 | 下次会话、下个任务，没人知道上一件到底验没验过 |
| P5 | 面板/台账没人专职维护 | 状态靠记忆，容易和事实脱节 |

## §2 改造后的循环（关键：只加一个节点，不动老板的习惯）

```
① Codex 商定任务 ──→ 写【任务书】落盘 队列/任务书/<任务号>.md
                        │
                        │  老板只需把任务书路径（一行）粘给 DSH
                        ▼
② DSH 按任务书施工 ──→ 写【交付物】落盘 队列/交付/<任务号>.md
                        │
                        │  老板只需说一句「验收 <任务号>」给 Claude Code
                        ▼
③ Claude Code 独立验收 ──→ 写【验收记录】落盘 队列/验收/<任务号>.md
                        │        （通过则：扫描 + 推送 + 核验远端，契约 §11）
                        │  老板只需把验收记录路径（一行）粘给 Codex
                        ▼
④ Codex 拿到验收结论 ──→ 做技术裁定 / 出下一份任务书
   （Codex 不再自己判「做得对不对」，那条已由独立第三方做了；他只判「接下来做什么」）
```

**老板的搬运动作没变（还是复制粘贴），但三点变了**：

1. 粘贴的不再是「大段 prompt」，而是**一个文件路径**（一行）。内容在文件里，不会走样。
2. 中间多了一个「验收」节点，由 Claude Code 完成，Codex 不必再做事实核查。
3. 每一棒都落盘，任何时刻断线，接手的人（或下一个会话）读文件就能续上。

## §3 三方各自怎么用（操作手册）

### 3.1 Codex（决策脑）

**开工时**：读自己的启动 prompt → 读 `01-契约` + `02-状态基线` → 读 `队列/验收/` 下最近几条验收记录（了解上一轮结论）→ 与老板商定任务。

**产出任务书**：

```
写文件：协作契约/队列/任务书/<任务号>.md
格式：用 01-契约 §3.1 的任务书模板（队列/_模板/任务书.md 可直接复制）
```

**收验收结论时**：读 `队列/验收/<任务号>.md` → 只做两件事：
- 结论是「通过」→ 商定下一步，出下一份任务书；
- 结论是「不通过 / 有条件通过」→ 决定是「让 DSH 返工（出修订任务书）」还是「调整方案」。

**Codex 不做的事**：不再自己跑命令核对 DSH 的说法（那是验收官的活）；不宣布完成；不登记面板。

### 3.2 DSH（施工队）

**接活时**：读任务书文件的**全部内容**，特别注意【可改文件】白名单和【禁止事项】。

**干活时**：严格在白名单内施工；跑任务书里列的【验收断言】命令，原文留存。

**交付时**：

```
写文件：协作契约/队列/交付/<任务号>.md
格式：用 01-契约 §3.2 的交付物模板
```

**DSH 不做的事**：不说「已完成」（只说「提请验收」）；不发验收结论；不扩大范围；不改定稿文档。

**DSH 的技术优势**：DSH 侧也挂了同一套 hook。它改定稿文档 / 跑 `git add -A` / 声称跑了没跑的命令，会被自己的门禁拦住或留痕——**这是机制，不是自觉**。

### 3.3 Claude Code（验收官）—— 本协议要定清楚的核心

**被叫到时**（老板说「验收 <任务号>」）：

```
第 1 步：读 队列/任务书/<任务号>.md（拿到验收标准）
第 2 步：读 队列/交付/<任务号>.md（拿到 DSH 的说法）
第 3 步：读 .hook-logs/<今日>.jsonl（拿到真实记录，核对 DSH 说法）
第 4 步：独立执行任务书里的验收断言命令（不采信 DSH 的输出，自己重跑）
第 5 步：逐条比对，写 队列/验收/<任务号>.md + 更新 02-状态基线.md
第 6 步：【面板更新】段写全（供 WorkBuddy 落库）；验收「通过」时 → 三道检查 → 推送 → 核验远端（契约 §11）
```

**第 4 步是核心**——「验收即命令」：命令不绿 = 任务没完成。验收官不评价代码写得好不好（那是 Codex 的技术裁定），只回答一个问题：**任务书里写的断言，现在是不是真的都成立**。

**验收官不做的事**：不改被验收物（发现问题只记录不代修）；不做决策（发现方案有问题只上报）；不写业务代码；**不直接改 wb-issues 面板**（输出【面板更新】建议块，由 WorkBuddy 落库）。

**触发方式（老板视角只有一句话）**：

| 场景 | 老板说什么 | 验收官（Claude Code）做什么 |
|---|---|---|
| 常规验收 | 「验收 S10-P0-1」 | 走上面 6 步 |
| 批量验收 | 「把队列里待验收的都验了」 | 扫 `队列/交付/` 下所有还没有对应验收记录的任务，逐个验 |
| 只查证据 | 「查一下 S10-P0-1 的证据」 | 只做第 3 步，核对日志与转述是否一致，出证据核对报告 |

### 3.4 WorkBuddy（面板 / 自动化官）—— 结论落账的地方

**落库**（把验收结论变成面板状态）：

- 输入：`队列/验收/<任务号>.md` 的【面板更新】段；
- 动作：更新 wb-issues 面板状态与评论（全体**唯一**有权）；
- 门槛：`running → done` 必须同时存在**验收记录** + `artifacts/<任务号>/manifest.json`，缺一不可（契约 §7.3）。

**其它职责**：每日 03:00 automation 巡检与 GitHub Issue 日报；脱敏命中 / 证据缺失 / 验收失败 / 漏跑的告警（Agent Mail + `ALERTS.md`）；交付物展示 / 预览支撑。

**落库时机**：① 老板说「同步面板」；② 每日巡检 automation 批量扫未落库记录；③ 验收完成后老板把记录转给 WorkBuddy。

## §4 任务的完整生命周期（状态机）

```
任务号出现在 Codex 对话里
   │
   ├─ Codex 写任务书 ──────→ [任务书] 落盘
   │                            │
   │                            ├─ 老板粘给 DSH ──→ DSH 施工 ──→ [交付物] 落盘
   │                            │                                    │
   │                            │                                    ├─ 老板说「验收 X」
   │                            │                                    ▼
   │                            │                            Claude Code 独立验收
   │                            │                                    │
   │                            │                          ┌─────────┴─────────┐
   │                            │                          ▼                   ▼
   │                            │                   [验收记录] 通过      [验收记录] 不通过
   │                            │                     （扫描+推送+核验         │
   │                            │                       远端，契约 §11）        ├─ 老板粘给 Codex
   │                            │                          │                   │  Codex 出修订任务书
   │                            │                          │                   │  （回到「任务书」节点）
   │                            │                          ▼
   │                            └──── 老板粘给 Codex ──→ Codex 做下一步决策
   │                                                    （并知会面板已更新）
   └─ 循环
```

**文件命名约定**：`<任务号>.md`，任务号沿用项目现有编号习惯（如 `S10-P0-1`）。

**队列目录结构**：

```
协作契约/队列/
├── 任务书/          ← Codex 写，DSH 读
│   └── S10-P0-1.md
├── 交付/            ← DSH 写，验收官（Claude Code）读
│   └── S10-P0-1.md
├── 验收/            ← 验收官（Claude Code）写，Codex 读（WorkBuddy 读来落库）
│   └── S10-P0-1.md
└── _模板/           ← 三份模板，复制即用
    ├── 任务书.md
    ├── 交付物.md
    └── 验收记录.md
```

## §5 与现有机制怎么咬合

| 已有机制 | 在队列协议里的位置 |
|---|---|
| 门禁 hook · PreToolUse deny | 管**不能做什么**（不改定稿、不危险 git）；队列协议管**该做什么、做到哪一步**。两者互补 |
| 门禁 hook · PostToolUse 留痕 | 给验收官提供**独立证据**（`.hook-logs/`），第 3 步核对用 |
| 门禁 hook · Stop 证据检查 | 防 DSH 空手交付（`artifacts/` 无新证据时会 block） |
| 面板（wb-issues） | 队列状态的外部视图。验收后由 WorkBuddy 按验收记录落库 |
| `artifacts/<任务号>/` | 交付物的证据区（命令输出、sha256），队列文件里只写指针 |
| CR 流程 | 任务若涉及定稿文档，任务书里必须写 CR 编号；人类批准后把路径写进 `cr-approved.txt`，门禁放行 |

## §6 边界情况怎么办

| 情况 | 处理 |
|---|---|
| **DSH 干到一半发现任务书有问题** | 停下，在交付文件里写「实施受阻 + 原因 + 建议」，结束本轮。由 Codex 决定改任务书还是换方案。不许自行扩大范围 |
| **Codex 不认可验收官的验收结论** | 走冲突仲裁：Codex 在验收文件末尾追加「异议」段（不删改原文），由老板裁定 |
| **任务很小（改一行注释）** | 可走轻量路径：Codex 可以在对话里直接指示，但**仍需**有交付与验收记录（用简化模板）。规模小不等于免验收 |
| **老板不在场，施工交付后** | V2.0 起由接棒器自动派验收（契约 §12）；只有做不做、看效果、上线三处闸门挂起等老板，5 分钟未处理推送手机 |
| **验收时发现 DSH 的转述与日志不符** | 立即判「证据缺失」，该任务作废重做。同时按契约 §8 升级给老板 |
| **任务涉及脱敏内容** | 队列文件全部在 `协作契约/` 下（工作区内），**不入仓库**，无脱敏顾虑。若要入仓库，先过 `hooks/policy-terms.txt` 扫描 |

## §7 自动化取舍（V2.0 改写）

V1.0 选择「队列 + 人工触发」，并约定积累 20+ 个任务后再议自动触发。截至 2026-10 已有 127 份任务书，条件已满足。V1.0 担心的三点，V2.0 这样处理：

| V1.0 的担心 | V2.0 的处理 |
|---|---|
| AI 之间连轴转，出错人来不及发现 | 返工最多两轮；等老板的事超过 5 件暂停开新工；每件状态在 Orca 与手机上实时可见 |
| 验收要启动会话，链路脆弱 | Orca 负责派工、心跳与完工回报；15 分钟无回报标疑似卡住；接棒器停机可退回手贴 |
| 老板从链路上消失 | 老板保留三处闸门：做不做、看效果、上线；任何时候可在 Orca 叫停 |

## §8 落地步骤

1. **老板批准本文**（连同 `待批准变更清单.md` 一起）。
2. 三份启动 prompt 各加一节「队列协议」（本轮已更新完毕）。
3. 三份模板就位（已落盘 `队列/_模板/`）。
4. **试跑一轮**：挑一个真实的小任务（建议 `S10-P2-1`，它是既有排队任务），完整走一遍队列流程，检验协议是否顺滑。
5. 试跑复盘后，把本文转正为契约 §11。
