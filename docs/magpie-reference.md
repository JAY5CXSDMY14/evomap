## 一、整体结构：四层文档 + 一个循环

| 文件 | 作用 |
|---|---|
| `CLAUDE.md` | 只有两行：`@AGENTS.md` 和 `@LESSONS.md`，保证 Claude Code 每次启动都自动加载 |
| `AGENTS.md` | 总索引：改代码前读什么（子系统文档、代码标准、社区 PR 规则、LESSONS），以及"哪段代码实际在跑"这类容易误判的知识 |
| `docs/code-standards.md` | 硬标准：验收条件 + review 清单 + 代码/GUI/commit 规范，reviewer 逐条检查 |
| `LESSONS.md` | 近期合并的工作哪里做错了、本来该被哪条规则拦住，改代码前必读 |
| `docs/subsystems/*.md` | 每个子系统的职责、运行路径、状态、契约；改到哪块，同一个 PR 里更新对应文档 |

6. 子系统文档和语义变更审查来自社区成员 Junjie Zhou 的 PR #889；code-standards 开头两张表是他在 Discord 提的六条审查规则。**方法论本身也接受社区贡献。** Junjie Zhou 本人 2026-10-13 补充：这两份文档是他在 Discord 上 @yetone 加的，灵感来自 dsh；**在此之前项目已经在用 agent 自动 review 和管理了**。也就是说，规则文档是在循环已经跑起来之后、按需要一层层长出来的，不是先设计好的。

## 三、LESSONS.md 的具体写法（最值得学）

1. **文件开头说明机制**：每晚复盘当天的 commit，找三类问题：
   - 哪些修复又被修了一遍（返工）；
   - 哪些不该被合并；
   - 哪些验证太薄。
2. **每天一段概况**：commit 数、发版范围、整体出了什么问题。例如"10-08 有 192 个 commit、18 次发版，每个 tag 都等到了绿色 CI"。
3. **教训按类别分组**：读懂报告 / 修一类而不是修一例 / 用户自己的文件和设置 / 验证 / 并发与测试 / 红测试与发版 / 合并与关闭。
4. **每条教训的固定格式**：
   - **加粗一句话规则**（祈使句，可执行）；
   - **证据**：具体 commit sha、issue 号，发生了什么、后来怎么修的；
   - 可选：该怎么做（具体命令或检查方法）；
   - **Done right**：做对了的正面案例，也带 sha；
   - **Seen N×（日期列表）**：这条在几个不同的日子被复盘发现。
5. **升级规则**：同一条教训在 **3 个不同日子** 被发现，就从 `LESSONS.md` 移到 `code-standards.md`，成为 reviewer 必查的硬标准；`LESSONS.md` 底部保留"已移入代码标准"一节，写明移动日期，并继续记录再次违反和做对的案例。
6. **复盘提交本身也要验证**：commit 里写"每个引用的 sha 都用 `git cat-file` 检查过；只改文档，没改代码"。

## 四、LESSONS.md 里的代表性教训（可直接借鉴）

### 读懂报告
- 先用报告人的原始场景（同一个 provider、套餐、界面）复现，再说修好了；检查的是用户的目标，不是中间步骤。例：一个 issue 来回 4 次，每次只修了截图里那一个 agent。
- 测试数据用报告人的原始字节，不要自己编一个"差不多"的样例。
- 修错误本身，而不只是改错误提示的措辞。

### 修一类而不是修一例
- 厂商专属的规则只作用于该厂商；加测试证明别的厂商不受影响。
- 一个限制要覆盖到达被保护对象的每一条路径。
- 隐私/安全豁免按数据在协议里的位置划定，不按字段名。
- 文档里写到的安全缺口就是未修 bug，同一个 commit 里开 issue。

### 用户自己的文件和设置
- 程序默认值永远不覆盖用户自己设的值；写之前列出该设置被读取的所有位置。
- 读取、解析、哈希失败等于"未知"，绝不当成"空"或"相等"（否则会误删数据）。
- 删除或覆盖凭证前，找出所有可能匹配同一 key 的记录。

### 验证
- 测试永远不加载真实的第三方页面，用保存下来的真实字节在本地起服务。
- 在 CI 用的同一个语言/运行时版本上复现问题。
- 以"保证某事"命名的测试，在保证被破坏时必须失败：合并前手动破坏一次看它变红。

### 红测试与发版
- 不要说"main 上也一样失败"了事：先 `git fetch`，写明跑的是哪个 sha；负载下才红也要开 issue。
- CI 绿了才打 tag，被取消的 run 不算；修复攒一批再发版。
- 两个会话在同一分钟修了同一个 flaky 测试：开工前在 issue 上声明"我在做"。

### 合并与关闭
- PR 自己的新测试失败，或 review 列出的问题没解决，不合并。
- issue 等报告人确认修好才关。
- 一个 commit 一个目标；超过 400 行的 commit 必须有正文，写改了什么、为什么、跑了什么。
- 两个会话永远不在同一个 checkout 里提交，各自用 `git worktree`。

## 五、code-standards.md 的验收条件（合并或发版前都要展示）

1. 一个**没有这次改动就会失败**的测试：把旧代码放回去，必须真实 FAIL（编译错误或跳过不算），再恢复看它通过。
2. 测试在沙箱里跑（临时 HOME），永远不读写真实配置和真实数据。
3. 格式化、vet、全量测试、各目标平台构建全部通过。
4. 改 UI 就在多个浏览器引擎、多种语言下跑 UI 测试。
5. 能用真实环境就用真实环境验证；做不到就明说，并且不对用户宣称可用。
6. 写明跑了哪些、各自输出了什么；没跑的列为"未跑"，不能省略。

截至 10-12，已有约 8 条教训从 LESSONS"转正"进了 code-standards（同类 bug 一起修、main 上的红测试马上修、合并前写清在哪个 commit 跑了什么等）。

**合并**：reviewer 拉代码，合到最新 main，重跑以上检查；在 PR 上写"在哪个 head 跑了什么"，然后用 `gh pr merge --match-head-commit <sha>` 合并，review 之后有新推送就要重新 review。

### 真实的合并评论长什么样（PR #1339，yetone 账号留下）

```markdown
Reviewed `9bfed616`, merged onto main `238f0d92`, then onto main `8df15fd4`. Merging.

**Harm check:** 改了哪些文件；有没有新网络请求、新文件读取、往外发数据。

**What was run**（构建标签、临时 HOME、固定缓存）:
- **Red check.** 把 main 上的旧代码放回去，新测试失败，并给出与报告人一致的报错原文；带上改动后通过。
- **Break check.** 故意把某个判断改成恒为 true，同一测试失败，证明另一半逻辑也被覆盖。
- Linux（Docker，非 root）：哪些包通过；以 root 跑时哪些失败、为什么与本改动无关。
- macOS：全量测试在哪个 merge 上通过；main 前进后又重跑了哪些包。
- vet（linux/windows）、gofmt 结果。

**Read:** 读代码得出的推理（写路径和检查路径现在一致等）。
**Not run:** 真实设备/真实账号没测的部分，明写。
```

要点：**Red check（回退必挂）+ Break check（故意改坏必挂）+ Not run（没跑就写没跑）**，并锁定审过的 sha 合并（`--match-head-commit`），审的过程中有人 push 合并就直接失败。

## 六、commit message 规范（整个循环的"审计日志"）

- **标题**：领域前缀 + 用户现在看到的行为 + 需求来源。例如 `gateway: ...（#1762, LumenXY on X）` 或 `(the owner: 为啥 Qoder CN 没有插件啊)`。
- **正文**：原因（含定位过程，如 pprof 数据）→ 改了什么 → 哪个测试没有改动会失败、失败信息 → 跑了哪些检查 → 已知的 flaky 或没测的部分。
- 这样第二天的复盘 agent 才能逐条判断"验证是否足够"。

## 七、人保留的权力

- **产品决定**：标准里写明"不要推翻维护者的有意决定"，遇到就留给维护者。
- **外部 PR**：改 CI/发布脚本、新增网络地址、读写凭证、加依赖等任意一条，都停下来等维护者看。
- **拉黑**：agent 只能附证据"提议"，维护者决定。
- 作者的中文指令直接引用进 commit，作为需求依据。指令基本是一句话吐槽，其余由 agent 补全成几百字的改动说明，例如：
  - `(the owner: 这个太丑了)`
  - `(the owner: 这里为啥是原生的 selector 而不是我们抽象的 ComboBox？)`
  - `(the owner: 这个为什么又加回来了啊？不是说 hover 的时候才出现吗？)`
  - `(owner: pr-preview 的时候有时候没有数据压根儿测不了，能否帮忙造一些假数据)` → 后来成了 CI 录屏用的假数据
- **人说哪里不对，agent 把它变成能验证的改动。**

## 七½、编排：作者本人的公开说明（2026-10-13）

仓库里看不到触发方式（4 个 workflow 都不是定时任务，LESSONS.md 更新时间 03:10、03:49、00:23、23:46、03:48、14:24、05:26 不规律）。yetone 在 X 上（https://x.com/yetone/status/2109855710444237018）说明：

> 其实我没有任何的魔法，甚至还特别简陋……就是用 Claude Code，然后用官方的 Opus 5.5 模型执行 loop 就可以了。我会并行执行图里的 3 个 loop，然后每晚抽一点时间铲铲屎（主要是 UI/UX 的问题），然后就没活儿了。

三条 `/loop` 提示词（截图原文要点）：
1. **GitHub + Discord**：盯 issue，判断值不值得修 / 实现；修完记得发版和回复，**不值得也要回复**；中转站广告商统一回复"感谢关注，日后会出相关合作方案"，**不能把第三方中转站直接加进产品**。盯 PR，逐行审代码和逻辑，**拉下来实际跑**，防"无脑用 Coding Agent 乱写、自己都没测过"的 PR；验证无误才合并，否则回复或关闭。监控 Discord 所有 channel，一个不漏，有价值就修 / 加功能、值得讨论就继续讨论；**要真实 @ 人**，只写名字对方收不到。
2. **X 反馈**：有价值或真实可复现的 bug 就实现 / 修复，上线后回复推文。**先用便宜的决策模型（jev）判断推文是否与 magpie 相关**，不相关直接忽略，不要转给主模型，太浪费 token。
3. **清理与复盘**：magpie 完全自动化改代码、合社区 PR，所以要定时清理屎山和恶意代码，防止项目难以维护以至变废；总结经验教训（哪些不该合、哪些验证不缜密）放进经验，防止以后的 agent 犯同样错误；**把老是提低质量代码的人拉入黑名单**。

评论区里作者的补充（同日）：
- **真实运行环境是关键**："你要把真实的运行环境提供给 Agent。比如你要有一台 macOS 电脑以及一台 Windows 电脑，然后在 Windows 上再创建个 Linux 虚拟机……让 Agent 每次都要在这三端上去真实地复现 bug 并去修复。" 追问后说明：**只有一端装 Agent**，其它机器不装，由这一个 Agent 去操作。
- **决策和审美靠什么**："比较依赖 Claude Code 那套简陋但有效的记忆系统和 repo 中的设计文档。开发之初跟 Claude Code 讨论、头脑风暴了很多内容，它都记在记忆文件里了，所以某些决策、审美偏好上，它可以做出跟我比较契合的决策和设计。" 有人问产品取舍谁来把关时，他指向 `docs/subsystems/` 这套 design system（由社区成员构建）。

仓库同日的相关更新：
- LESSONS 新增 "A squash merge's message is written, not GitHub's default"：#852、#1028 的默认 squash 信息约 520KB（分支合过 main，列出了所有 commit），#1028 自己的运行记录根本没进 git。规则：`gh pr merge --squash` 必须给 `--subject` 和 `--body-file`，推送前确认 `git log -1 --format=%B | wc -c` 最多几 KB。
- contributors.md 作者分三级：Blocked（5 条拉黑条件 + 固定关闭语）、Reviewed with extra care、新增 **Watched**（有用但反复出同类缺口，合并前专查点名的缺口，不算拉黑）。首个 Watched 作者的必查项是"手动改坏看新测试变红"和"grep 漏掉的兄弟路径"。
- 关于 loop 冲突，LESSONS 早有 "Two sessions never commit from the same checkout"（10-09 两个会话共用 index 提交了彼此的文件），每个会话自己的 worktree。

评论区提出、作者**没有回答**的问题（自建时要自己解决）：3 个 loop 改同一仓库如何避免冲突（worktree？）；3 路 loop 的权限 / deny 规则是否共用；Issue 里夹带恶意脚本怎么办；云端还是本地常驻；token 成本。另有评论指出：长期运行积累的新记忆可能污染早期的核心决策；子系统文档过期会把 agent 带偏。

结论：
- 夜审 = 第 ③ 条 loop，不是 cron；"错题本"由这条 loop 写。
- 编排是**按渠道拆 loop**，每条 loop 内部自己走完分诊→实现→验证→合并→发布→回复。
- 人的工作：方向、闸门，以及**每晚人工过 UI/UX**。
- 两个前提常被忽略：**真实的多端复现环境**，以及**开发初期沉淀下来的产品决策与审美记忆**。
- 仍未公开：loop 间隔、各 loop 是否用独立 worktree、jev 的具体配置。evoloop 对应的落地方案见 `docs/orchestration.md` 的 L0 档与 `prompts/loops/`。

## 八、这套循环的本质

```
执行（agent 写、测、review、合、发）
  → 留痕（commit 写清来源和验证）
  → 夜间复盘（agent 读当天 commit，找返工、错误合并、薄弱验证）
  → 写成带证据的教训（LESSONS.md，计次）
  → 出现 3 天升级为硬标准（code-standards.md）
  → 下一轮 agent 开工前必读（CLAUDE.md 自动加载）
  → 回到执行
```

**关键不在于让 agent 自动写代码，而在于让 agent 的错误自动变成下一轮 agent 的约束。**

## 九、请对照我们现在的循环回答

1. 我们的 agent 开工时会不会自动加载一个总索引和教训文件？
2. 我们的 commit 或 PR 是否记录需求来源、验证过程、哪些没跑？复盘 agent 能不能只靠这些判断验证够不够？
3. 我们有没有夜间复盘？复盘找的是哪几类问题？
4. 教训是否带具体证据（sha/issue）和出现次数？有没有"出现 N 次升级为硬标准"的规则？
5. 验收是否要求"回退就会失败"的测试，而且真的回退验证过？
6. 写代码和 review 是否由不同的 agent 做？reviewer 是重新跑过，还是只看 diff？合并时是否锁定 review 过的 sha？
7. 多个 agent 并行时，是否各用 worktree、开工前声明认领？
8. 测试是否和土布的真实 Postgres、MinIO 数据完全隔离？
9. 哪些决定必须留给人？写进文档了吗？

**请列出我们已有的、缺失的，以及建议优先补的前 3 项。**
